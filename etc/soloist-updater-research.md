# Soloist release/updater implementation brief

**Scope:** Read-only inspection of `soloistd` and the local `soloist-pi` checkout. No public network or Spotify services/credentials were accessed. The Soloist CDN asset itself was not fetched, so its complete archive contents and live response headers are unknown. **Path convention:** unqualified `soloistd` source paths below are rooted at `/home/sirianni/src/github.com/MopigamesYT/soloistd/`; unqualified `soloist-pi` paths are rooted at `/home/sirianni/src/github.com/sirianni/soloist-pi/`. Thus, for example, `download.go:22` means `/home/sirianni/src/github.com/MopigamesYT/soloistd/download.go:22`.

## 1. Authoritative release contract

- `soloistd` defines `https://soloist-builds.spotifycdn.com/` as the base URL and maps Go `arm64` to `soloist_release_arm64.tar.gz`. It concatenates these directly, making the arm64 URL **`https://soloist-builds.spotifycdn.com/soloist_release_arm64.tar.gz`**. There is no version segment or query string in the construction. **Source:** `/home/sirianni/src/github.com/MopigamesYT/soloistd/download.go:22,32-43,60-62`.
- This is an architecture-specific asset URL, not an architecture field in a manifest. The other implemented mappings are `amd64` → `soloist_release_x86_64.tar.gz` and `arm` → `soloist_release_arm32.tar.gz`; other Go architectures error. **Source:** `download.go:32-43`; mapping tests: `download_test.go:14-31`.
- README and the Python plan describe the archive as the stable/current build, but the implementation's concrete contract is simply the fixed asset URL above. There is **no release-manifest URL, checksum endpoint, version API, or separately constructed redirect URL** in this code. `/home/sirianni/src/github.com/MopigamesYT/soloistd/README.md:104-108`; `plan-python.md:9-11`.
- The code expects a **gzip-compressed tar** (`gzip.NewReader`, then `tar.NewReader`) and extracts the first member whose cleaned name is `soloist`. Its name normalization cleans the path, converts separators to `/`, and removes a leading `./`; only that matching member must be a regular tar file (`TypeReg`/`TypeRegA`). **Source:** `download.go:77-85,218-252`.
- The implementation does not establish the complete production archive member list: it silently skips nonmatching entries and returns immediately after the first matching executable. Thus, whether the CDN archive contains other members—and whether there are duplicate `soloist` entries—is **unknown from the checkout**. Existing archive fixtures contain one regular `soloist` member; the only explicit archive-type test rejects a symlink named `soloist`. **Source:** `download_test.go:47-75,78-98`.

## 2. HTTP behavior and validators

1. **Freshness check:** `checkForUpdate` issues a `HEAD` to the same architecture asset URL with `User-Agent: soloistd/<version>`, a 30-second client timeout, and accepts exactly HTTP `200 OK`. It does not send `If-None-Match`/`If-Modified-Since`; `304` is therefore not treated as “unchanged” and is an error. No HEAD body or content type is used. **Source:** `download.go:114-143`.
2. **Download:** `installLatest` issues `GET` to the same URL, sets the same User-Agent, uses a five-minute client timeout, and accepts exactly `200 OK`. It does not check `Content-Type`. **Source:** `download.go:45-75`.
3. **Response metadata:** From HEAD or GET responses it reads `ETag`, `Last-Modified`, `X-Amz-Checksum-Crc32c`, and `ContentLength`. ETag/checksum/Last-Modified may be absent; code does not require any of them. Checksum is only copied into local metadata and compared—it is **not computed or verified against the downloaded bytes**. No separate checksum resource is used. **Source:** `download.go:24-30,146-153,156-170`.
4. **Comparison order:** Archive names must match. If both sides have an ETag, equality/inequality decides immediately; otherwise, if both have CRC32C headers, those decide; otherwise, if both have Last-Modified values, both Last-Modified and Content-Length must match. If no comparable pair is available, metadata is considered different. A present-but-different ETag does not fall back to another validator. **Source:** `download.go:156-170`; tests cover ETag precedence and archive mismatch: `download_test.go:34-45`.
5. **Persistence / download trigger:** The installed response's headers are saved as JSON in `release.json`; metadata is written to a temp file in the same data directory and renamed into place. A successful HEAD match plus an executable installed file skips GET. Missing/unreadable metadata, changed validators, or a file that fails the executable test trigger download. The HEAD response decides whether GET is needed; the GET's own headers are what get persisted. **Source:** `download.go:106-108,134-143,172-210`.
6. **Forced refresh:** Exit-status-10 handling calls `installLatest` directly, not `checkForUpdate`, so it downloads unconditionally even when saved validators would match. **Source:** `supervisor.go:50-64`; this is tested with an unavailable HEAD endpoint and a working GET: `supervisor_test.go:21-82`.
7. **Limits and transport details:** The GET path wraps the HTTP body in a `LimitedReader` with a 256 MiB limit and allows an extracted executable of 1 byte through 512 MiB. HEAD timeout is 30 seconds; GET timeout is five minutes. There are no application-level retries. **Source:** `download.go:67,77-89,94-95,124`.
   - The 256 MiB check is based on bytes consumed by the parser and checks `N == 0` after extraction. Since extraction returns as soon as it finds `soloist`, the code does not prove it consumed or bounded the *entire* response/archive in that case. `Content-Length` is not separately enforced as a download limit. This is a safety gap, not a claim about actual CDN archive size.
   - The app sets only User-Agent; it defines no custom redirect, TLS, `Accept-Encoding`, or `Content-Encoding` policy. The `http.Client`/default transport behavior therefore applies; the source does not document an endpoint-specific redirect or encoding contract. The archive is gzip regardless of any HTTP-level content encoding. Python should retain ordinary HTTPS certificate validation, bound the actual streamed bytes, and avoid depending on unverified header/redirect assumptions.

## 3. Install/validation algorithm

- **Default paths:** XDG environment variables override the roots; otherwise home-relative defaults are used. The managed executable is `$XDG_DATA_HOME/soloistd/bin/soloist` (fallback `~/.local/share/soloistd/bin/soloist`); metadata is `$XDG_DATA_HOME/soloistd/release.json`. Config defaults under `$XDG_CONFIG_HOME/soloistd/config.json`; Soloist data/cache use `$XDG_DATA_HOME/soloist` and `$XDG_CACHE_HOME/soloist`. **Source:** `/home/sirianni/src/github.com/MopigamesYT/soloistd/paths.go:18-52`; documented defaults: `README.md:89-100`.
- **Staging:** Create the managed binary directory with mode `0755`, then a `.update-*` temporary directory *inside that directory* (same filesystem). Temporary-directory cleanup is deferred. Extract to its `soloist` file using create-exclusive mode `0755`, then explicitly chmod it to `0755`. **Source:** `download.go:50-58,83-92,238-250`.
- **Validation:** Run the staged executable as `<temp>/soloist --version`, combining stdout and stderr, with a 15-second context timeout. It passes only if process exit is successful **and** combined output starts exactly with `soloist `; output after the prefix is not parsed. **Source:** `download.go:94-102`.
- **Replacement / durability:** After validation, `os.Rename` moves the staged binary onto the managed path, which is a same-directory-filesystem replacement on the intended Linux deployment. Earlier download, extraction, chmod, or validation errors occur before this rename and leave the prior binary in place. The code does not call `fsync` on the staged binary or containing directory. Metadata is saved *after* binary replacement; if that save fails, the command reports an error even though the new executable has already replaced the old one. Metadata temp-file creation, chmod `0644`, write, close, and rename are used, but there is also no `fsync`. **Source:** `download.go:103-110,184-210`.
- **CDN fallback / “usable” binary:** `ensureBinary` accepts any `stat`-visible regular file with at least one execute bit; it does not invoke `--version`. `runDaemon` ensures that file first, then attempts the startup freshness check; if that check errors, it logs a warning and continues with the installed file. Thus, an executable file is the code's practical fallback criterion, not proof that it can run correctly. If no such file exists, startup attempts an install and returns an error if that fails. **Source:** `/home/sirianni/src/github.com/MopigamesYT/soloistd/commands.go:225-232`; `supervisor.go:26-35`; executable predicate: `download.go:213-216`.

## 4. Compatibility and safety gaps

- **Reuse/adapt:** The fixed arm64 asset mapping, HEAD-vs-GET flow, optional validator fallback, local metadata representation, direct forced-download path for status 10, staged validation, and rename-based binary installation map directly to the updater increment. The source's local HTTP tests and fixture archive helper are also useful patterns. **Sources:** `download.go:32-43,114-210,218-253`; `supervisor_test.go:21-135`.
- **Do not copy periodic daemon behavior:** `soloistd` checks at startup **and every six hours**, and a changed build can stop/restart a currently running process. `soloist-pi` explicitly requires startup-only checks, no background polling, and no release-driven restart. Keep its status-10 forced refresh, but do not port `watchForUpdates` / the periodic restart path. **Source:** `supervisor.go:14,33-38,68-115`; Go docs: `README.md:104-108`, `doc/soloistd.1:32-43`; Python requirements: `/home/sirianni/src/github.com/sirianni/soloist-pi/etc/deployment-plan.md:12-29`.
- **Tighten archive and byte bounds:** Go safely writes only the named member rather than arbitrary archive paths, but skips all other members (including non-regular types under other names), permits cleaned aliases such as `./soloist`, accepts the first match without duplicate/trailing-archive validation, and can stop before verifying the full compressed response. For the Python security requirement, impose hard bounds on bytes actually received and decompressed, validate the archive through EOF (or deliberately specify a strict member policy), and test duplicate/traversal/link/type cases. Do not interpret the Go behavior as evidence of the real asset's exact member inventory.
- **Add integrity / robust fallback as deliberate choices:** Go trusts TLS plus executable validation; its CRC32C header is not checked against the payload and is not cryptographic integrity verification. It has no custom retry policy. The fallback test is only regular-file-plus-execute-bit. Python's local plan requires usable-binary fallback and defensive updates, so define whether “usable” includes a bounded `--version` probe; preserve old binary and metadata behavior on all pre-install failures. Consider metadata/binary crash consistency and `fsync` only if required for the Python contract; neither is provided here.
- **Explicit `soloistd update` is unconditional:** It resolves default paths and calls `installLatest` directly, without a freshness HEAD check; therefore there is no “no update” result. Even if validators are unchanged it fetches/validates/replaces the binary. Success prints the download notice and `Installed <version output>`; failures propagate to the CLI, which prints the error and exits `1` (usage errors exit `2`, cancellation exits `0`). The command does not itself restart a running Soloist process. **Source:** `commands.go:147-156`; `download.go:60-110`; `main.go:58-104`.
- **Current `soloist-pi` status:** Its deployment plan contains the updater requirements, but README and CLI still say the backend / `update` command are not implemented; existing tests are scaffold/placeholder tests. The current README describes TOML config (not the JSON wording in the separate `plan-python.md`), so avoid conflating config format with updater release metadata. **Sources:** `/home/sirianni/src/github.com/sirianni/soloist-pi/etc/deployment-plan.md:1-6`; `README.md:1-5,27-38`; `src/soloist_pi/cli.py:39-58`; `/home/sirianni/src/github.com/sirianni/soloist-pi/AGENTS.md`.

## 5. Recommended `soloist-pi` acceptance tests

All updater tests should use a local HTTP server, generated gzip/tar fixtures, and temporary paths/fake executables, consistent with `/home/sirianni/src/github.com/sirianni/soloist-pi/etc/deployment-plan.md:30-32` and `AGENTS.md`.

1. Assert arm64 constructs `/soloist_release_arm64.tar.gz`; reject any unsupported target if architecture is configurable. Check User-Agent and that startup freshness uses `HEAD`, followed by `GET` only when required.
2. Cover same/different ETag; ETag priority over Last-Modified; CRC32C and Last-Modified-plus-length fallbacks; missing validators; corrupt/missing metadata; and a matching release that produces no GET. Verify metadata is atomically replaced and reloadable.
3. Assert a status-10/forced refresh does a GET even when HEAD or saved validators indicate unchanged, and does not rely on any periodic request. Add an integration test proving no HTTP requests occur while a long-running fake Soloist is active.
4. Exercise HTTP failures (non-200 HEAD/GET, unavailable server, truncated body, timeout), redirects according to the chosen policy, and missing/unknown content length. Confirm startup continues offline with a validated installed executable, while first install without connectivity fails clearly.
5. Build fixtures for expected regular `soloist`, missing member, `./soloist` and traversal-like names, symlink, hard link, directory/FIFO, unrelated entries, duplicate `soloist`, oversized executable, oversized compressed response, oversized decompressed content, and malformed/truncated gzip/tar. Verify no archive-controlled path is written and no partial install is committed.
6. Fake executable validation cases: exit 0 with `soloist ...` succeeds; nonzero exit, wrong/empty output, timeout, and execution error fail. For every failed case, assert existing binary bytes and mode remain unchanged. On success assert installed mode and new contents; also inject metadata-write failure to specify expected binary/metadata consistency.
7. Carry over update-process edge cases from Go tests: changed release causes one GET and next check causes none (`soloistd/supervisor_test.go:84-135`); HEAD outage does not block status-10 refresh (`:21-82`). Add Python-specific expiry-after-long-runtime, bounded immediate repeated expiry, later retry after a successful run, and SIGTERM-forwarding/kill-timeout cases required by the Pi plan (`etc/deployment-plan.md:14-19`).
